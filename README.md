# io guardo — Website handover

Source code for the io guardo landing page at [ioguardo.mx](https://ioguardo.mx).

**The live website is currently hosted on Firebase Hosting under the previous maintainer's Firebase project.** The incoming company should create a Firebase project in its own Google account, deploy this code there, and update the domain's DNS records in GoDaddy. Receiving the repository does not transfer Firebase or domain access.

## Current setup

| Item | Configuration in this repository |
| --- | --- |
| Website domain | `ioguardo.mx` |
| Existing Firebase project | `ioguardodesarrollo` (the default in `.firebaserc`) |
| Framework | Next.js 16, React 19, TypeScript, Tailwind CSS 4 |
| Build output | Static files in `out/`, generated by `npm run build` |
| Hosting configuration | `firebase.json` publishes `out/` and rewrites unmatched paths to `/index.html` |
| Contact form | FormSubmit, currently addressed to `ioguardoadmon@gmail.com` |

`next.config.ts` enables `output: "export"` and disables server-side image optimization. This deployment uses Firebase **Hosting** for static files; it does not require Firebase App Hosting, a running Next.js server, or Cloud Functions. The application currently has no environment variables or Firebase SDK configuration to set up.

## 1. Prepare the handover

- Give the incoming team the repository, including `package-lock.json`, `firebase.json`, `.firebaserc`, and the assets in `public/`.
- Confirm the team can create and manage Firebase projects using company-controlled Google accounts.
- Arrange access to the GoDaddy account or delegated DNS access for `ioguardo.mx`.
- Keep the previous maintainer available to release the custom domain from the existing Firebase Hosting site during the switch.
- Save a copy of the existing DNS records and keep the old Firebase deployment available until the new site has been verified.
- Confirm who will manage the contact inbox and the site's Google Search Console property. These are separate from Firebase Hosting.

Generated folders such as `node_modules/`, `.next/`, `out/`, and `.firebase/` are not the source of truth. Build a fresh copy from the source for deployment.

## 2. Run and build locally

Install Node.js and npm. Next.js 16 in this repository requires Node.js 20.9 or later; use a supported Node.js release that also meets the Firebase CLI's requirements.

From the repository root:

```bash
npm ci
npm run dev
```

Open [http://localhost:3000](http://localhost:3000). Stop the development server when finished.

Check and build the production files:

```bash
npm run lint
npm run build
```

The build must produce `out/index.html`. Internet access is needed during the build to download the Google fonts used in `app/layout.tsx`. The `npm run start` script runs `next start`, which is not the preview workflow for this static export; use the Hosting emulator below.

Main files to maintain:

- `app/page.tsx`: page content and contact form.
- `app/layout.tsx`: metadata, canonical URL, business structured data, and Google site verification.
- `app/globals.css`: styling.
- `public/`: images, floor plans, `robots.txt`, and `sitemap.xml`.

## 3. Set up Firebase in the new company's account

1. Sign in to the [Firebase console](https://console.firebase.google.com/) with the company's Google account and create a new project. Record its **project ID**, which can differ from its display name.
2. Open **Build → Hosting** and complete the setup for a Hosting site. Use the project's default Hosting site for the configuration below.
3. Install the [Firebase CLI](https://firebase.google.com/docs/cli), sign in with the company account, and confirm the new project appears:

   ```bash
   npm install -g firebase-tools
   firebase login
   firebase projects:list
   ```

   If the CLI is signed in to the previous maintainer's account, run `firebase logout` before signing in again.

4. In the incoming team's copy of `.firebaserc`, replace the old project ID with the new one:

   ```json
   {
     "projects": {
       "default": "YOUR_NEW_FIREBASE_PROJECT_ID"
     }
   }
   ```

   Replace `YOUR_NEW_FIREBASE_PROJECT_ID` in every example with the actual ID. Commit the updated `.firebaserc` to the new team's repository. Leaving `ioguardodesarrollo` as the default risks targeting the previous project.

5. Keep the existing `firebase.json` and `next.config.ts`. This repository already has Hosting configuration, so it does not need `firebase init hosting` again. The directory to publish is **`out`**, not `public` or `.next`.
6. Preview the freshly built site locally:

   ```bash
   firebase emulators:start --only hosting --project YOUR_NEW_FIREBASE_PROJECT_ID
   ```

   Open the local URL printed by the CLI, check the page and images, then stop the emulator.

7. Deploy to the new project:

   ```bash
   npm run build
   firebase deploy --only hosting --project YOUR_NEW_FIREBASE_PROJECT_ID
   ```

8. Open the **Hosting URL printed by the deploy command** and verify the site before changing DNS. The default site normally uses `https://YOUR_NEW_FIREBASE_PROJECT_ID.web.app`.

The explicit `--project` flag selects the deployment destination even if a different project is active locally. See the [Firebase Hosting deployment guide](https://firebase.google.com/docs/hosting/quickstart) for the underlying setup workflow.

## 4. Connect the domain to the new Firebase project

1. Agree on a switch window with the previous maintainer after testing the new deployment. A custom domain can be attached to only one Firebase Hosting site at a time; moving it can temporarily interrupt service.
2. In the new project's **Hosting** page, select **Add custom domain** and enter `ioguardo.mx`.
3. Use **Quick Setup** for a transfer from another Firebase Hosting site. Coordinate removal of the domain from the old Hosting site when required to complete the move. Keep the old project and deployment for recovery.
4. Copy the verification and routing records shown by the new project's wizard. Apply them in GoDaddy as described below, then return to Firebase to verify ownership and complete setup.
5. If `www.ioguardo.mx` should also work, add it separately in Firebase and select the option to redirect it to `ioguardo.mx`. Apply its requested DNS records too.

Use the exact records supplied by Firebase; do not reuse the old project's verification values or assume that changing an IP address alone transfers the domain. See [Firebase's custom-domain instructions](https://firebase.google.com/docs/hosting/custom-domain).

## 5. Update DNS in GoDaddy

1. Sign in to [GoDaddy Domain Portfolio](https://dcc.godaddy.com/), select `ioguardo.mx`, and open **DNS**.
2. Confirm the domain uses GoDaddy's nameservers. If another provider hosts authoritative DNS, make the record changes there instead. Connecting Firebase Hosting does not itself require changing nameservers.
3. Save the current records before editing. Use **Add New Record**, or edit the relevant existing record, and copy the values from Firebase's wizard.

| Record requested by Firebase | GoDaddy Name field | GoDaddy Value field |
| --- | --- | --- |
| TXT for domain ownership | `@` if Firebase requests the root domain; otherwise the supplied host prefix | Exact verification string from the new project |
| A for the root website | `@` | Exact IPv4 address supplied by Firebase; add every requested value |
| Record for `www` | `www` | Use the record type and destination Firebase supplies; use CNAME only if instructed |
| Additional verification record, if requested | Supplied host prefix, such as `_acme-challenge` | Exact value from the wizard |

In GoDaddy, `@` means `ioguardo.mx`, and `www` means `www.ioguardo.mx`. Enter host prefixes without appending the domain again. A CNAME destination is a hostname, without `https://` or a path; do not create a CNAME at `@`. Leave TTL at its default unless the migration plan specifies otherwise.

4. Replace or remove conflicting website A, AAAA, CNAME, parking, or forwarding entries only as needed for the hostnames being moved. Preserve unrelated records, especially email MX, SPF, DKIM, and DMARC records. Update the Firebase ownership TXT record as instructed without removing other TXT records.
5. Save the changes, then finish verification in Firebase. Keep the required Firebase ownership record in DNS after verification.

GoDaddy's detailed instructions: [A records](https://www.godaddy.com/help/add-an-a-record-19238), [TXT records](https://www.godaddy.com/help/add-a-txt-record-19232), and [CNAME records](https://www.godaddy.com/help/add-a-cname-record-19236).

## 6. Verify the handover

DNS changes and HTTPS certificate provisioning are not immediate. Firebase advises allowing up to 24 hours for certificate provisioning after the domain points to Hosting. Wait for **Connected** in the [Firebase custom-domain status](https://firebase.google.com/docs/hosting/custom-domain) before declaring the switch complete.

- Visit `https://ioguardo.mx` and confirm HTTPS works without certificate warnings.
- Check `https://www.ioguardo.mx` if configured, including its redirect.
- Verify the latest content, images, floor plans, navigation, mobile layout, `robots.txt`, and `sitemap.xml`.
- Coordinate a contact-form test with the inbox owner and confirm delivery. The form posts to FormSubmit, independently of Firebase, and its success URL currently returns visitors to `https://ioguardo.mx/#contacto`, including when tested on the temporary Firebase URL.
- If the contact inbox changes, update the form action in `app/page.tsx` and the email in `app/layout.tsx`, complete any verification requested by FormSubmit, then rebuild and redeploy.
- Arrange Google Search Console access and review `metadata.verification.google` in `app/layout.tsx` with the new owner.
- If the domain itself changes, update `SITE_URL` in `app/layout.tsx`, the form's `_next` URL in `app/page.tsx`, `public/robots.txt`, and `public/sitemap.xml` before rebuilding.
- Confirm the incoming team can deploy independently before retiring the previous hosting setup.

If the new Firebase URL fails, resolve the build or deployment first. If that URL works but the custom domain fails, check authoritative DNS, conflicting records, domain ownership, and certificate status in Firebase. Restoring old DNS alone may not restore service after detaching a Firebase custom domain; recovery may also require reconnecting it to the old Hosting site with the previous maintainer.

## Future deployments

Run from the repository root after making changes, replacing the placeholder with the new company's project ID:

```bash
npm ci
npm run lint
npm run build
firebase deploy --only hosting --project YOUR_NEW_FIREBASE_PROJECT_ID
```

Firebase publishes the contents of `out/`; always rebuild before deploying so the uploaded files match the source.
